# Product story acceptance

Build and test every applicable row below, not just a successful opening review. Read shared rows and only the selected Earn/Blue/Midnight rows alongside the corresponding product reference. These are required UI behaviors and acceptance checks; the product references retain exact routes, units and variant schemas. In particular, use the verified `/v0` Vault V2 user-position list and chain-prefixed Midnight Actions selectors, not inferred versions or bare-ID Actions paths.

Use controlled, non-signing fixtures for unfunded wallets, liquidity limits, price changes, liquidation events and confirmed/indexed responses. Keep fixtures dev/test-only and label fixture versus live evidence. A read-only run cannot prove real execution: report those lines `UNVERIFIED`, not passed. Preserve open design thresholds, Max safety buffer, Midnight interest accounting and Blue liquidation-event gaps; test supported mechanics without inventing production values.

## Fixture contract and common mistakes

- Feed recorded/synthetic **API-shaped** inputs through the same parser, math, state machine and renderer as live data, with a final hard block on wallet signing/sending. A fixture button that only throws “signing disabled” does not exercise preparation. Include signature-required → continuation → prepared success, ordered final review, failed proof and receipt → stale index → reconciled response; keep missing live execution `UNVERIFIED` even when fixtures pass.
- `simulation-failed` must deliver the successful HTTP envelope `data.status: "simulation_failed"`, `data.simulation.status: "failed"`, `data.simulation.failure.message`, and no executable calls, then exercise the normal failed-action handler/details toggle. Assert zero wallet prompts/sends; a generic insufficient-balance or fixture-block exception is a different test.
- Earn reward fixtures need campaign IDs and `breakdowns[]` containing matching and foreign campaigns, claimed/pending amounts and unequal token prices/decimals. Test native `apy:null` separately from request failure, no campaign separately from Merkl failure, and sparse/untrusted hourly buckets. Assert an attributed `amount=1.52`, `pending=0.03`, `claimed=0.20` token earns **1.55**, claims **1.32**; a foreign/unattributed entry must not increase this vault's earned USD. Verify Total earned and non-annualized return, not just that rewards render.
- Force fixture needs supported adapter capacity and nonzero simulated `penalty_assets`/remaining shares, not just low liquid balance that makes the force button unreachable. Inspect both force variants and supported in-kind or the precise API exclusion. Do not “fix” an exact-assets request by adding unsupported `max_penalty_bps`; this field belongs to the full-position force schema. Test share-token permits/approvals, max uint, small available amounts and narrow review layout without overflow.
- Borrow populated fixtures must enter through shares/market totals and `borrow_net_cost_assets`, not overwrite already-calculated debt/interest. Spy on slider-repay/maintenance/full-close bodies before the no-send boundary; time quotes during release/out-of-order replies. Run a scheduler/monitor pass against a local sink and clock-driven band/maturity transitions. Seed paginated event/history payloads with fixed timestamps, partial/full/roll and remaining positions, then navigate away/back; a banner using today's clock and hard-coded seized amounts does not test event mapping/persistence. Blue heuristic and Midnight interest/design gaps remain unverified, not invented.
